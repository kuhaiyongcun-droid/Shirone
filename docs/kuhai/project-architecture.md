# 项目架构与迁移

状态：拟实施方案。产品定位已确认，目录和路由尚未迁移。

## 模块职责

| 范围 | 职责 | 首版边界 |
| --- | --- | --- |
| 网站外层 | kuhai 的身份、语言、主舰入口、内容路由 | 单一网站与部署入口 |
| 主舰模块 | 舰船、星球、灯光、旋转、舱区高亮与剖视 | 整舰外观与一个可进入档案室 |
| 档案室模块 | 文章列表、阅读、目录、搜索、分类 | 以 Shirone 为基础保留横幅、侧栏、圆角卡片和阅读结构 |
| 共同设计 | 标识、材质色彩、语言和返回主舰动作 | 全站统一美术，博客维持阅读所需的低开销 |
| 研究档案 | 设定证据、结构推演、资产登记、决策、测量 | 归档到 docs/kuhai |

其他舱室按实际内容逐个加入。舱室间切换先返回主舰；档案室内部文章列表、文章详情和返回不受限制。研究总图可以包含动力、维护等区域，但不自动形成网站功能。

## 现有工程约束

本仓库目前是完整 Shirone 源码工程，使用 Astro、Svelte 与 Swup；Astro 配置由 `src/integration/` 驱动，存在源码模式与 npm 包模式。路由、配置覆写和持久页面壳有共同约束，不能只把目录改名就视为已模块化。

在现有 Astro 工程中渐进增加主舰模块，先建立入口与生命周期边界；待边界验证后，再评估将博客提取为独立本地包。第一阶段无需建立多个独立前端应用。

## 拟定代码归属

| 位置 | 用途 | 当前状态 |
| --- | --- | --- |
| src/features/flagship/ | 3D 场景、输入、舱区数据、质量调整、资源生命周期 | 拟新增 |
| src/layouts/FlagshipLayout.astro | 主舰专用布局，避免自动装载博客侧栏与持久脚本 | 拟新增 |
| 现有博客 pages、layouts、components | Shirone 档案室实现，先沿用已有组织方式 | 已有，尚未整体迁移 |
| public/assets/flagship/ | 已确认可分发的网页模型、纹理、海报与版本清单 | 拟新增 |
| docs/kuhai/ | 产品与研究文档 | 本批建立 |

新模块不直接侵入 Shirone 的原子组件和 Markdown 管线。主题源码改动继续遵守已有打包与组件契约。品牌字段、包标识和远程仓库 URL 要分别处理；不能在未检查主题自识别逻辑前直接修改 package.json 的名字。

## 拟定路由

| 入口 | 中文 | 英文 |
| --- | --- | --- |
| 主舰 | / | /en/ |
| 档案室入口 | /blog/ | /en/blog/ |
| 博客文章与分类等 | /blog/ 下的对应子路径 | /en/blog/ 下的对应子路径 |

以上路径是迁移建议，尚未生效。选择 blog 作为技术路径是为了与 Shirone 已有的 archive 归档页区分；页面显示名称仍为档案室。实施前盘点旧文章链接、分页、标签、分类、RSS、搜索索引、canonical、sitemap 和语言切换映射，再确定兼容路径或重定向。首页变为主舰后仍需提供档案室入口。

进入博客后，主舰的渲染循环、事件监听、音效和 GPU 资源应停止并释放。直接打开博客链接时不下载主舰模型或渲染引擎。博客页面之间继续按 Shirone 的 Swup 生命周期运行；跨模块导航首先考虑完整页面导航，待资源释放验证后再评估连续镜头切页。

## 实施顺序

1. 提交本批项目说明与研究档案，确立产品名称和文档归属。
2. 单独核对并同步已发布站点的中文化修改，避免在入口改造中遗漏现有功能。
3. 在功能分支实现主舰布局、模型接口与一个档案室入口；对直接访问、返回、窄屏和无 WebGL 的路径做验证。
4. 迁移博客路由并核对内容、语言、搜索与旧链接；保持博客内部原有布局。
5. 接入经过美术确认的资产，完成设备测量后发布。

可在后续将 GitHub 仓库更名为 `kuhai-site`。改名是单独操作，需要一起核对 remote、工作流、文档链接、Pages 路径和托管绑定，不作为本批已完成事项。
