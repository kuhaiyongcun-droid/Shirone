# 画质与性能方案

状态：工程设计建议，尚未实机测量。任何帧率、体积与设备覆盖范围都不能视为现有模型的测试结果。

## 设备要求

实时 3D 在访客的设备上执行，主要占用 GPU、共享内存或显存，也会消耗 CPU、网络、电量和散热余量。服务器性能不能代替浏览器的渲染性能。目标是让普通核显和主流手机保留完整的旋转与舱区选择，高性能设备提供更精细的画面。

成本同时受几何与绘制调用、屏幕像素数量、材质计算、阴影、透明层和后处理影响。只统计模型面数不能判断是否流畅。

## 拟定质量档位

| 模式 | 保留内容 | 可调整内容 | 初始目标 |
| --- | --- | --- | --- |
| 标准 | 完整舰体、星球、关键光影、旋转、剖视 | 中等模型与纹理、限制实时阴影和后处理 | 参考桌面 1080p 交互目标 60 fps |
| 轻量 | 同一舰型、舱区和主要美术构图 | 降低渲染分辨率、细节与粒子、以烘焙和环境光照替代部分计算 | 参考核显和手机交互目标 30 fps |
| 高画质 | 提升关键细节、反射与阴影质量 | 按资源余量追加纹理和效果 | 基于实测逐项开启 |
| 静态 | 高质量主舰海报与可访问的舱室入口 | 停用实时三维 | 无 WebGL、显著性能不足或用户选择时使用 |

这些是设计目标，不是硬件型号承诺。默认自动选择，提供一个低存在感的画质设置。分档同时参考能力和暖机后的持续帧耗时，不能只凭显卡名称判断，也不要在短时波动时反复切换档位。

## 优化策略

- **模型与贴图**：母版与网页导出分开；使用 LOD；将适合烘焙的微小结构转为法线与遮蔽信息；共享材质、合并静态批次和重复件实例化。
- **光照**：保留主方向光与关键动态阴影；静态舱内间接照明可烘焙；环境反射保持与光源一致。母版可离线高质量渲染，网页不以全场景实时路径追踪为默认方案。
- **显示分辨率**：给实际绘制像素设置上限；高 DPI 屏幕不能无限跟随 devicePixelRatio。按性能适度调整分辨率，避免仅为了抗锯齿大幅增加像素成本。
- **透明与后处理**：剖视仅处理当前舱区；严格控制透明叠层、全屏辉光与大气效果。行星与星空采用与镜头距离匹配的资产。
- **加载**：先展示海报和入口，再加载必要 3D 资产；高画质与内部舱区按需加载。贴图使用适配设备的压缩格式，模型网络压缩与 GPU 内存占用分别测量。
- **生命周期**：离开主舰或页面隐藏时停帧；进入博客释放不用的纹理、几何、渲染目标和监听；WebGL 上下文丢失时恢复或转为静态入口。

## 暂定资源预算

首轮可交互资产以 10 MiB 以内的网络传输量为优化起点，高画质补充资源分批加载；这是项目预算建议，需在视觉样板完成后校正。记录压缩下载体积、解码峰值与估算 GPU 占用，不把它们混为一项。

例如一张 4096 × 4096 的未压缩 RGBA8 贴图约占 64 MiB，完整 mipmap 链约 85.3 MiB；这是按像素与通道推算的单贴图理论值。压缩 GPU 格式、通道数、运行实现和渲染缓冲会改变实际用量，网页下载的 JPEG/WebP 文件大小不能直接代表显存占用。

## 测量与验收

测试至少包含一台普通核显电脑、一台独显电脑和一台主流手机；如可用，加入用户自己的核显电脑与小米 12S。记录设备、浏览器、分辨率、档位和网络条件。

覆盖初次访问、缓存访问、连续旋转、剖视、进入和退出博客、窗口缩放、前后台切换及数分钟持续运行。观察帧耗时分布、卡顿、资源峰值、下载、温升与耗电；分别记录 CPU 与 GPU 相关瓶颈。

不会将无头环境或脚本模拟结果宣称为用户设备帧率。博客直接访问必须验证不下载主舰资产；主舰返回和恢复后不能积累重复渲染循环。

## 技术依据

- [MDN WebGL best practices](https://developer.mozilla.org/en-US/docs/Web/API/WebGL_API/WebGL_best_practices)：资源预算、较小绘制缓冲、绘制批次与压缩纹理。
- [Khronos KTX](https://www.khronos.org/ktx/)：网络交付与 GPU 压缩纹理。
- [Three.js WebGLRenderer](https://threejs.org/docs/pages/WebGLRenderer.html)：绘制尺寸、渲染统计、着色器编译与资源释放。
- [Three.js LOD](https://threejs.org/docs/pages/LOD.html)：按距离切换几何细节。
