# kuhai 主舰开发计划

版本：第一版。日期：2026-10-12。状态：开发计划草案，沿用已确认的项目方向；阶段验收细则与新增制作安排待后续样板校正。

最终目标是把主舰做成 kuhai 个人网站的核心作品：远看有战舰海报的气势，靠近能读出装甲、设备和人员活动的尺度，旋转到侧后方与腹部仍然可信；访客通过实际舱区进入自己的内容空间。Shirone 负责其中的档案室博客。

当前用户反馈是“整体感觉还行”，但舰体仍像乐高拼接模型，缺少真实战舰的结构密度。这轮反馈认可继续推进的方向，不代表最终造型和质感已验收。后续重点是补足有用途的中尺度结构，再完善材质与光影。增加渲染采样或换用显卡不会自动生成这些内容。

## 最终目标与首版范围

| 方面 | 首个正式版本的目标 | 具体判断方式 |
| --- | --- | --- |
| 网站定位 | kuhai 的个人空间，休伯利安号式主舰承担首页 | 身份、主舰与档案室形成统一体验；Shirone 作为博客基础继续保留署名与许可 |
| 远景 | 清晰的舰型、厚重体量、电影海报式构图与光影 | 桌面与手机首屏都以主舰为主体；星球和特效不抢主体，不靠极暗画面掩盖结构 |
| 中近景 | 有工程关系和服役痕迹的科幻巨舰 | 可分辨装甲层、设备、连接、检修与尺度参照；明显减少大块均匀拼接和塑料感 |
| 全角度外观 | 舰首、舰桥、两侧、舰尾、顶部和腹部均完成可见部分 | 在允许的旋转和缩放范围内，没有明显草模面、悬空零件、穿插或空洞 |
| 太空环境 | 恒星、舰体、行星、云层与大气形成一致场景 | 光向和明暗关系连贯；发光、辉光与粒子服务主体，不遮掉金属细节 |
| 舱室交互 | 主动旋转，实际舱区高亮和局部剖视，点击进入 | 悬停不改变整舰或相机；触屏不误触；返回恢复先前观察位置 |
| 档案室 | 一个可用的博客模块，保持 Shirone 的阅读结构 | 横幅、侧栏、圆角卡片、文章与目录继续可用；去掉二次元素材，统一舱室气氛 |
| 访客性能 | 普通核显和主流手机有可用体验，强设备可追加画质 | 按设备实测分档；无 WebGL 或加载失败仍能从静态主舰进入博客 |
| 长期维护 | 制作源、网页资产、脚本和文档能持续迭代 | 新环境可恢复、修改、导出和发布，版本与来源可追溯 |

首版集中完成整舰外观、太空场景及一个可进入的档案室。其他舱室保留空间和数据扩展能力，有实际内容后逐个开放。舰桥、工程舱、观测甲板、休息舱、舰长室仍是候选功能，名称和完整清单未定。

全舰内部建立连贯的功能规划；高精度室内只制作剖视或进入时能看到的区域。整舰自由漫游、所有隐藏房间、战斗模拟和真实轨道模拟不在首版范围。采用官方可见设计作为依据，缺失区域明确记为网站创作补全，不宣称完成官方整舰复原。

首页保留少量必要提示、设置和可访问入口；博客内部由博客设计会话维护，默认暗色方向与战舰材质协调。舱室之间必须先返回主舰再切换，博客内列表与文章的正常导航保留。

| 网站接入 | 主舰在独立私有审阅站点 | 正式主入口与档案室路由尚未接入；本计划不改变现有博客发布 |

当前旋转版使用简化 PBR，制作源的程序化漆面与粗糙度尚未完整转入网页。同时，制作源本身仍缺少足够的中尺度结构。因此要同时改进资产制作和网页转换，不能把全部差距归因于实时渲染。

最近一次云端记录为 1280×800、48 samples 的 CPU 样片约 25 秒，峰值进程内存约 1.5 GiB。它说明当前小样可继续在云端推进，不能代表最终整舰成本或访客性能。

## 消除乐高感的制作标准

| 层次 | 具体制作内容 | 取舍规则 |
| --- | --- | --- |
| 大尺度 | 舰首、肩部、舰桥、推进段的体量和过渡 | 保持已选方向；局部精修若暴露比例问题，先修体量，再堆表面细节 |
| 中尺度 | 装甲厚度与嵌套、承力连接、舱门、机库、设备槽、传感器、喷口内部和维护通道 | 优先投入；部件之间要有用途和连接关系，避免均匀重复方块 |
| 小尺度 | 检修盖、紧固件、密封、标牌、局部管线、焊缝与维修补板 | 按镜头可见尺度制作，管线有起终点，装饰不能盖住主要结构 |
| 材质 | 漆面、裸金属、橡胶、玻璃与发光器件的差异 | 统一纹理尺度；磨损与维修位置相关，避免全舰均匀撒噪点和掉漆 |
| 人体尺度 | 成组灯窗、标准舱门、扶手、通道和人员参照 | 舱内外使用同一尺度体系；研究样板放大的舱区需重新核对 |
| 细节分布 | 大装甲留白，舰桥、连接、机库和动力区域提高密度 | 丰富度来自有主次的结构，不以填满每块表面为目标 |

每次评审至少保留中性灯光和正式气氛灯光两组。中性灯光用于检查造型、厚度、接缝与材质；气氛灯光用于检查最终表现。不能只交一张有利机位的暗色海报。

## 分阶段开发

### 阶段一 参考补全与局部设计

围绕舰桥侧舷和相邻装甲整理现有资料，补查缺口。优先级为官方游戏画面和概念资料、实际读到的设定集与小说、创作者研究、现实舰船和航天工程。已有材料继续利用，研究须对应具体设计问题，不以来源数量代替结论。

产出为带出处的局部参考板、部件功能草图、统一尺度表，以及官方依据、创作者解释和网站原创补全的区分。官方资料相互冲突时选定主参考并说明理由；没有取得正文或图版的资料不得作为已读证据。现有素材登记继续记录来源、作者、许可和使用位置。

完成条件：局部部件能解释用途、连接、装甲分层和内部对应，不存在必须等到全舰制作后才解决的比例冲突。

### 阶段二 接近成品的舰桥侧舷样板

以现有舰桥侧后研究为起点，精做“舰桥侧舷＋相邻装甲＋一段设备或维护结构”。集中改进承力连接、内凹设备、厚度、遮挡、尺度和材质差异，随后添加适量小细节。

交付可编辑 `.blend`、纹理、固定机位前后对比、中性光与气氛光预览，以及同一区域的轻量网页导出。至少检查整舰尺寸、中景和允许的最近观察距离；制作源与网页使用对应机位比较，明确哪些细节保留、近似或省略。

完成条件：在中景已能明显减少大块拼接感；近景能读出装甲下的结构；远景仍清晰；网页样板也有可辨认的提升。以这轮结果建立整舰质量基准。若仍像玩具，继续调整本区域，不把未成熟方案批量铺满全舰。

### 阶段三 整舰结构深化

按“舰首与前肩 → 舰桥和中段 → 两侧与腹部 → 舰尾与推进器”逐区扩展样板标准，复用已有合适部件。允许不同区域有不同密度和维修历史，避免整舰机械复制同一组细节。

每一区域交付同机位对照、整舰观察和局部结构检查，并更新网页审阅版本。固定检查前上方、侧面、后方、顶部、腹部及档案室位置。内部功能总图同步核对可用体积、舱壁、通道和外部开口。

完成条件：允许观察的各方向都有一致的完成度，主要连接与轮廓成立；不存在依靠灯光隐藏的草模区域。只规划但不可见的隐藏房间不展开高精度制作。

### 阶段四 全舰材质与太空光影

建立并统一装甲漆、裸合金、设备、玻璃、密封、灯具和标识材质，按区域制作 UV、贴花和旧化。继承已验证的材质样板，减少重复纹理、错误比例和一片灰色塑料感。

光照同时检查舰体体量、凹槽纵深、玻璃和金属反射、舱内透光与引擎发光；行星、云层和薄大气沿用一致恒星方向。先稳定真实结构，再控制辉光、曝光、尘粒和背景亮度。

交付整舰材质母版、贴图清单、横竖屏场景、关键角度静帧与网页对应版本。高清海报可在资源允许时制作 2560×1440 或 3840×2160 输出，具体采样与批次通过小样决定；这些输出规格不等于网页实时渲染分辨率。

完成条件：远中近景层次清楚，材质能区分，灯光不淹没结构，星球与主舰关系协调。源文件中的精细效果需有网页实现或明确取舍，不能只停留在离线图片。

### 阶段五 网页资产与性能收敛

网页转换从阶段二开始；本阶段负责整舰的系统优化。整理拓扑、UV 和材质归并，按距离与设备配置细节等级。轮廓、明显遮挡、重要开口和剖视外壳保留真实几何，微小凹凸按可见尺度转为法线等贴图。

外部使用实时光照所需的材质数据，不把固定视角的高光和整张场景阴影直接画进颜色图。稳定的内部间接光可单独烘焙，并检查剖视状态下的遮蔽和亮度。评估 KTX2/Basis 纹理、现有几何压缩、重复件实例化与按需加载，每项以画质和实测成本决定采用。

交付标准、轻量与静态版本；高画质作为按资源余量加载的增强。检查加载、解码、首帧、持续旋转、剖视、切换与资源释放，避免只统计压缩文件大小或模型面数。

完成条件：达到下文约定的设备目标，关键结构与美术辨识度保留；直接访问博客不下载主舰资产，离开主舰不残留渲染循环与不用的 GPU 资源。

### 阶段六 档案室交互与网站接入

主舰工作负责舱区位置、外壳与内部结构、选择、进入和返回；博客工作负责 Shirone 内部视觉、内容和阅读。共同确定入口地址、返回动作、语言映射与素材接口，避免两个设计会话覆盖同一职责。

保留当前悬停不移动相机、触屏先选择再进入和返回恢复观察位置的规则。高亮与剖视贴合实际舱区，不用脱离舰体的导航卡片替代。区域结构、hit area 和可见反馈须一致。

按 [架构与迁移](../project-architecture.md) 核对中文化分支、旧链接、文章、分类、搜索、RSS、语言切换、canonical 与 sitemap，再实施主舰和博客路由。拟定 `/blog/` 路径仍属于迁移方案，不能写成已生效地址。仓库重命名另行处理。

完成条件：主舰进入档案室、文章阅读、返回主舰形成闭环；深链接和前进后退正常；各舱室保持独立。保留原博客回滚入口，正式替换首页前完成整站审阅。

### 阶段七 整体验收与首版发布

汇总真实浏览器和设备记录、最终美术对照、资产来源、迁移包和回滚版本。解决影响视觉或导航的已知问题，再将通过验收的主舰设为正式首页。

交付物包括可用网站、私有审阅版本记录、可编辑制作源、网页资源和构建脚本、研究与素材清单、设备测试结果及维护说明。当前计划的归档不等于这些阶段已完成，也不触发正式站点发布。

## 云端与本地显卡分工

云端继续自主完成资料整理、局部设计、程序化结构、材质样板、低分辨率预览、网页转换和交互开发。每个制作阶段记录实际耗时、内存和失败原因；下一步不需要先连接家中电脑。

当小样显示高清渲染、批量烘焙或复杂材质迭代明显受限时，列出具体任务、已测耗时或失败、预计批次和交付物，准备可迁移任务包。优化组织和分批处理后仍存在瓶颈的部分，再交由家中 RTX 3060 Ti；不因云端慢降低最终美术目标，也不默认购买服务或租用 GPU。

只有用户明确表示家中电脑已连接后，才核实目标机器、访问授权、Blender、驱动和实际可用显存。先运行同场景小样和单张贴图烘焙，检查耗时、内存余量及成品差异，再决定分辨率、采样和批次。不在其他电脑上启动重负载，也不把设备型号当作无限容量保证。

GPU 用于提升制作效率和可承担的渲染工作量。最终细节仍来自结构、材质和灯光的制作；网页访客不需要具备同一张显卡。

每份交接包包含可编辑 `.blend`、相对路径或打包贴图、脚本、锁定依赖与版本、相机和渲染设置、启动步骤、预期产物、实际测试记录与校验值，并在另一目录验证可打开和重建。源码与文档进入 GitHub；大型制作资源按现有持久任务包方式交付，仓库保存版本和获取记录。

## 网页性能与验收口径

沿用 [画质与性能方案](performance.md) 的初始目标：标准桌面 1080p 交互目标 60 fps，轻量核显和手机交互目标 30 fps。首轮可交互资源以 10 MiB 以内的传输量为优化起点，高画质和内部空间分批加载。这些是待验证的预算，不是当前已达成数据，也不构成对所有设备的承诺。

参考设备至少包含普通核显电脑、独显电脑和主流手机；可用时加入用户的小米 12S。记录具体硬件、浏览器、视口、内部渲染分辨率、档位和网络条件，覆盖冷加载、缓存加载和至少五分钟持续操作。报告帧耗时中位数与高分位、卡顿、真实绘制调用、解码内存、估算 GPU 资源及释放情况，不只报告平均帧率。

| 验收项 | 通过条件 |
| --- | --- |
| 操作 | 拖动不误进入，双指缩放不误点，悬停前后相机和整舰变换不变，返回恢复视角 |
| 可用性 | 键盘可选择与进入，焦点清楚；减少动效偏好得到响应；失败和静态模式有博客入口 |
| 加载 | 海报与基本入口先可用，关键资源按需加载；性能设置可手动调整且不反复跳档 |
| 连续使用 | 旋转、剖视、进入返回和前后台切换不造成持续卡顿或资源不断累积 |
| 博客隔离 | 直接打开文章不加载主舰引擎和模型；文章导航、搜索、目录与语言行为正常 |
| 美术 | 同机位源与网页对比通过，全角度无明显空洞和穿插，关键细节没有在导出时整体消失 |
| 可恢复性 | 新目录能打开源文件和重建网页版本；发布有可恢复的前一版本 |

真实设备测量由可用且获得授权的环境执行。脚本投影、资产校验和离线渲染只能证明各自检查项，不能替代浏览器表现与访客设备帧率。

2. 一份在现有模型上深化的可编辑局部样板，保留前版以便比较。
3. 同机位中性光与气氛光、远中近景对照，展示改进来自哪里。
4. 同区域的网页旋转样板或对现有私有预览的对应更新，验证细节在网页中仍能成立。
5. 制作耗时、内存、模型和贴图体积、转换差异及下一批问题清单。

排期按可验收成果推进，先由局部样板测出实际制作与转换成本，再估算整舰剩余工作。高质量目标不等于无边界增加复杂度；每轮完成一个明确的视觉或体验改进，并留下可复用资产。
